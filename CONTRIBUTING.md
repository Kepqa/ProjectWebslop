# Как вести разработку

## Ветки

- **`main`** — то, что сейчас на сайте. Каждый мерж в неё сам выкладывается на GitHub Pages.
  Напрямую в `main` не пушим — только через PR.
- **Фича-ветка** на каждую задачу, от свежего `main`: `<игра>/<что-делаем>` латиницей через дефис.
  Игра — `survivors`, `duel`, `gladiatorial` или `hub`; для общего (сборка, звук, CI) — `common`.
  Примеры: `gladiatorial/shield-parry`, `survivors/boss-rework`, `hub/sort-cards`.
  Сессии Claude Code создают ветки `ccr-…` сами — это такие же фича-ветки.
- Одна ветка — одна задача. Ветка живёт дни, не недели: большую фичу режь на несколько PR.
  Недоделанное, но безопасное можно мержить, если игрок этого не видит (например, за `?debug`).

## Цикл задачи

1. `git switch main && git pull && git switch -c <игра>/<задача>`
2. Коммиты на русском. Перед пушем — `npm run build`.
3. PR в `main`. CI прогоняет `npm run build`; красный — не мержим.
4. Перед мержем: обнови ветку от `main`, подними версию и допиши CHANGELOG (см. ниже).
5. Мерж — автор сам, когда CI зелёный. Если PR трогает чужую игру или общий код — ждём ревью
   владельца (GitHub попросит его автоматически, см. `.github/CODEOWNERS`).
6. После мержа ветку удаляем (кнопка в PR).

## Версии и CHANGELOG

Версия одна на весь хаб, в `package.json` (SemVer): новая возможность — `0.X.0`, правка — `0.X.Y`.
Изменение, которое игрок не заметит (рефакторинг, документация, CI), версию не поднимает.

Поднимаем версию **в последний момент перед мержем**, после обновления ветки от `main`, а не в начале работы:
так две параллельные ветки не займут один и тот же номер. Запись в CHANGELOG начинается с названия игры.
